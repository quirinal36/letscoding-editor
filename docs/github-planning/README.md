## 범위와 등록 기준

MVP는 Monaco 기반 정적 HTML/CSS/JS 작품 편집→AI 변경 승인→라운지 배포다. TS는 편집/언어 서비스만 포함하며 React/TS 실행 번들링, 서버 빌드, 터미널, 공동 편집, 모바일 에디터는 포함하지 않는다. 미리보기 모바일 폭 전환은 모바일 에디터 지원과 별개다.

명세의 P1도 현재 출시 후보에 유지한다. 단계 5의 P2 4개도 자동으로 후속으로 옮기지 않았다(I-041). 명시적 후속 ID 4개와 번들링 검증 후보 F-005는 기한 없는 후속 백로그로 둔다. 이미지 생성은 C-03 검증 불가 시 제외안을 제시할 수 있으나 현재 준비 문서에서는 포함한다.

계획서의 HMAC 방식 B·공유 Supabase·학생 중심 MVP는 **권장안/계획안**이다. 체크리스트 A-03~05가 닫히기 전 확정 사실로 취급하지 않는다. 같은 계정 사용과 브라우저 쿠키 공유도 별개이므로 로그인 검증에 포함한다.

## GitHub 등록 방식

1. I-001~003으로 결정 기록을 만들고 범위·담당·착수일을 확정한다. 기술 검증 I-004~007을 진행한다.
2. 기존 라벨에 더해 `type:epic`, `type:feature`, `type:task`, `type:decision`, `type:spike`, `priority:P0/P1/P2`, `status:blocked`, `scope:follow-up`을 등록 후보로 사용한다. 기본 라벨만 현재 존재한다.
3. M0~M5 마일스톤을 생성한다. 일정 확정 전 due date는 비워 둔다. 기한 없는 후속 마일스톤은 만들지 않아도 된다.
4. E-00~10을 추적용 에픽 이슈로 만든다. 여러 마일스톤에 걸친 에픽은 최초 목표 마일스톤을 쓰거나 비워 두며 개별 자식의 마일스톤을 기준으로 진행률을 본다. E-08은 라운지 저장소에 둔다.
5. 52개 후보를 대상 저장소에 등록하고 준비 키→실제 번호/URL 대응표를 만든다. 부모 본문 task list 또는 지원되는 sub-issue 관계로 연결한다. 저장소를 넘는 의존성은 URL로 연결한다.
6. 각 이슈에 근거 ID·수용 기준·의존성·검증 방법을 유지하고 에픽은 자식 이슈 완료로 닫는다. 기능명세서의 구현 상태는 증거 확인 후 별도 갱신한다.

L-001~004는 라운지 저장소에 등록했으며 에디터에 중복 구현 이슈를 만들지 않았다. 등록 시 원격 `yudanah/letscoding_lounge`와 규약·기존 이슈를 확인하고 기존 #23·#172를 참고 링크로 연결했다. 마일스톤은 에디터 M0~M5 6개와 라운지 연동용 1개다. 원본 Google Sheets와 기존 라운지 이슈는 변경하지 않았으며 커밋·푸시도 하지 않았다.
