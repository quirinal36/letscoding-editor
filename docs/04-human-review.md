# 구현 후 사람이 준비·검토할 항목

> 2026-10-04 · 사용자 결정: 추천 기반 구성 채택, AI 예산은 개발 이후 결정, 계정은 사용자가 준비하고 `.env.local`을 채움. 초기 자동 검사는 외부 계정·유료 모델 없이 수행했고, 이후 운영 DB를 transaction rollback으로 검증했다. 학생 2명의 실제 로그인·저장·격리와 Gemini 유료 모델 호출은 [운영 검증 기록](./07-live-verification.md)에서 확인한다.

## 2026-10-07 수업 과정 기록·학생 체크포인트 (1·2단계)

- 목적: 교사가 세특 작성의 관찰 근거로 학생의 진행 과정을 볼 수 있도록, 열람(3단계) 전에 기록부터 남긴다. 계획 문서: 「스튜디오·라운지 수업 과정 기록과 교사 열람 기능 개발 계획」(Google Docs).
- 저장 출처: 리비전마다 `student`(직접 저장)·`ai`(변경안 승인·자동 반영, 메시지 ID 포함)·`import`(ZIP·파일 가져오기, 브라우저가 알리는 참고값)·`template`(생성·복제)와 바뀐 파일 경로를 남긴다. 출처는 서버가 요청 종류로 정하며 브라우저가 주장할 수 있는 값은 `import`뿐이다. GitHub 가져오기 저장(`editor_github_sync`)은 아직 출처를 남기지 않는다.
- 학습 이벤트: 미리보기 오류 발생(세션당 같은 오류 1회, 메시지 앞 300자), 오류가 있던 뒤 3초 동안 오류 없는 실행(해결), 한 번에 20줄 이상 붙여넣기(줄 수만), 변경안 거절(서버 기록)을 남긴다. 코드 원문은 저장하지 않는다. 프로젝트당 하루 200건을 넘으면 버린다.
- 체크포인트: 상단 “여기까지 완성”에서 현재 저장된 파일 전체를 스냅샷으로 남기고 선택 입력 한 줄 회고(200자)를 받는다. 같은 리비전에서 다시 누르면 새로 만들지 않는다. 목록에서 “이 시점 보기”로 그 시점 작품을 sandbox 미리보기로 연다. 라운지 게시가 성공하면 서버가 게시 시점 스냅샷(회고 포함)을 남긴다. 스냅샷은 30일 버전 정리 대상이 아니며 보존 기간은 학교 약정 후 정한다.
- 운영 적용 순서: `integration/process-record.sql`을 라운지 migration으로 옮겨 staging 검증 → 운영 적용 → 에디터 `EDITOR_PROCESS_RECORD=true` 설정. 설정 전에는 기존 RPC만 호출하므로 현재 운영과 호환된다. 개인정보 처리방침에 기록 항목(출처·이벤트·스냅샷·회고)을 추가한 뒤 켠다.
- 남은 범위: 교사 열람(수업 단위 권한·타임라인, 3단계)과 교사 메모·성취기준(4단계)은 라운지 저장소 작업이다. 스냅샷은 큰 텍스트를 DB jsonb에 사본으로 저장하므로 실제 사용량을 보고 Storage 이전 여부를 판단한다. 학생이 프로젝트를 삭제하면 기록도 함께 삭제된다.
- `npm run check`(31개), `npm run build`, `npm run test:e2e`를 실행했다. PGlite에서 출처·변경 경로, 이벤트 상한·크기 제한, 스냅샷 중복 방지·회고 길이, 본인 외 RLS 거부, 스냅샷 참조 Storage 보존을 검사하고, 데모 브라우저에서 체크포인트 생성·중복 방지·게시 스냅샷·이전 시점 미리보기·새로고침 후 유지를 검사했다. 운영 DB 적용과 배포는 하지 않았다.

## 2026-10-07 라운지 프롬프트 실행 연결

- 메뉴 선택과 직접 입력 모두 동일하게 처리한다. “라운지 랭킹”·“라운지 로그인 사용자 이름” 요청에는 Lounge Deploy 0.3.0의 공식 SDK/API 지침을 서버 시스템 메시지에 추가한다. 랭킹은 실제 점수와 최종 종료 지점을 읽고 `LetscodingRanking.submitScore`를 연동하도록 하며, 점수·종료 조건이 없으면 임의로 게임 규칙을 만들지 않는다. 이름은 `/play/{id}/`의 동일 출처 `/api/me?projectId=...`와 `textContent`만 사용한다.
- 라운지 관련 작업은 공개 MCP에서 현재 정책을 조회하며 조회 실패 시 이전 정책으로 대체하지 않는다. 순수 ZIP·정책 검사 요청은 유료 모델 없이 현재 작품의 ZIP 생성·재해제 검사, 실행 파일 metadata 분석, 최신 정책 재조회와 전체 파일 manifest 최종 검증을 수행한다. 문서·이미지·데이터는 framework 분류 대상에서 제외하고 전체 ZIP manifest에 포함해 검사한다. 학생 소스·ZIP 원문·사용자 이름·비밀값은 MCP에 보내지 않는다.
- 코드 연동과 ZIP을 함께 요청하면 파일 변경 후 검증 도구를 호출한다. 생성한 ZIP 해시와 브라우저에서 반영된 현재 파일의 ZIP 해시가 일치할 때만 다운로드하며, 검증 실패·정책 변경·미승인 변경·동시 수정은 다운로드 성공으로 처리하지 않는다. 자동 라운지 게시를 수행하지 않는다.
- 합성 HTML 예제로 실제 공개 MCP의 정책 조회·분석·최종 검증 PASS를 확인했다(정책 `2026-08-27.1`). 유료 모델·실제 학생 계정·운영 게임 점수 제출은 호출하지 않았다. 로컬 sandbox는 외부 SDK/API 접근을 막으므로 로그인 이름과 실제 점수 등록은 라운지 게시 후 확인한다.
- `npm run check`(29개), `npm run build`, `npm run test:e2e`(데모 10개·Auth/GitHub 12개)가 통과했다. 공식 지침의 실제 모델 요청 포함, ZIP·검사 시 유료 호출 없음, 정책 조회 실패·변경·최종 실패·ZIP 폴더 항목 제한과 비밀 파일 metadata 차단을 검사했다. 브라우저에서는 실제 다운로드 바이트의 해시 일치, 검증 실패·현재 파일 해시 불일치 시 다운로드 차단을 확인했다. 운영 배포는 수행하지 않았다.

## 2026-10-07 AI 작업 중단 시 완료 범위 보존

- AI는 독립적으로 사용할 수 있는 완성된 파일 묶음과 PROJECT.md를 순서대로 제안할 수 있다. 성공한 묶음만 누적하며 같은 파일의 후속 수정은 최신 내용으로 합친다. 뒤 묶음의 입력·파일 검증이 실패해도 앞 묶음을 덮어쓰지 않는다.
- 응답 한도·연결 오류·단계 종료로 남은 작업이 있으면 `partial` 응답으로 완료 범위와 다음 작업을 보관한다. 화면과 승인 API는 완료된 부분을 원자적으로 자동 반영하며, 전체 교체 승인·stale revision 차단은 유지한다. 사용자가 직접 중단한 요청은 자동 반영하지 않는다.
- 잘린 코드·JSON은 복구해서 적용하지 않는다. 완성된 묶음이 없으면 파일을 바꾸지 않으며, 전체 교체·삭제·이름 변경·이미지 제안은 기존 확인 절차를 따른다. 계속 작업하려면 “이어서 진행해줘”라고 요청한다.
- 가짜 공급자 검사로 연속 생성→같은 파일 수정→후속 실패, 응답 한도, 잘린 입력, 금지 파일, 연결 끊김, 실패 후 정상 복구를 확인했다. 실제 유료 모델 호출·운영 배포는 수행하지 않았다.
- `npm run check`(27개), `npm run build`, `npm run test:e2e`(데모 9개·Auth/GitHub 10개)가 통과했다. 브라우저 검사에는 부분 변경 자동 반영, 전체 교체 수동 승인, 다음 작업 안내와 새로고침 후 파일·대화 보존을 포함한다.

`npm ci` → `npm run dev` → `http://localhost:3100`에서 로컬 데모를 연다. 첫 클릭 게임, 파일/폴더 작업, “버튼 색을 파랗게 바꿔줘” → 비교 → 승인, 미리보기, 배포 ZIP 검증을 확인한다. 데모 데이터는 **이 브라우저의 IndexedDB**에 저장된다. 다른 기기/서버로 자동 이전되지 않으므로 중요한 작업은 ZIP으로 보관한다. 데모에서는 실제 모델·라운지 작품·배포 링크를 만들지 않는다.

## 환경 설정 시 확인할 점

- `EDITOR_DEMO_MODE=true`: 개발 데모. 클라우드 검증할 때 `false`로 바꾼다. production에서는 무조건 무시한다.
- `NEXT_PUBLIC_*` 설정 변경은 앱 재빌드/재배포가 필요하다. 로컬 설정을 채운 뒤 개발 서버를 다시 시작한다.
- 서버 저장: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`. service role은 서버 전용이다. staging 미확인 상태에서 운영 DB를 개발 기본값으로 넣지 않는다.
- DB 스키마: 에디터 REST/RPC의 기본 schema는 `editor`. 계정 조회는 `public.profiles`를 명시하며 Auth와 Storage는 기존 API를 사용한다. SQL 적용과 API schema 노출을 완료했다. 운영 DB transaction에서 저장·버전·CAS·예산 정산·다른 사용자 RLS·서버 RPC 권한을 확인하고 시험 데이터를 모두 rollback했다. 서버 REST 조회 HTTP 200, 세션 없는 익명 요청 HTTP 401(`42501`)을 확인했다. 코드 검사는 12개 테스트 통과이며, 직전 스키마 변경 배포에서 build와 E2E 5개도 통과했다.
- 실제 AI: `EDITOR_AI_ENABLED=true`, 전용 `OPENROUTER_API_KEY`, 허용 모델, 양수인 `EDITOR_AI_DAILY_LIMIT_USD`, `EDITOR_AI_MONTHLY_LIMIT_USD`, `EDITOR_AI_MAX_TURN_USD`. 모델 가격이 확인되지 않거나 예약 예산을 확보하지 못하면 호출을 중단한다.
- 비전 입력: 선택한 비전 모델의 보수적 이미지 입력 비용을 측정한 뒤 `EDITOR_AI_IMAGE_INPUT_RESERVE_USD`를 설정한다. 이미지 생성도 `EDITOR_IMAGE_ENABLED=true`, 출력 모델과 `EDITOR_AI_IMAGE_OUTPUT_RESERVE_USD`를 추가로 요구한다. 이미지 생성 비용·크기 지원은 모델마다 실제로 검증한다.
- 앱 예약 한도는 공급자의 청구 상한을 대신하지 않는다. 중단/응답 유실 때 실제 비용을 모르면 예약 금액을 보수적으로 기록한다. 공급자 key/workspace 한도와 월 알림을 별도로 설정하고 미정산 예약은 공급자 로그와 대사한다. 임의로 0원 처리하지 않는다.
- 배포: `EDITOR_DEPLOY_ENABLED=true`, `LOUNGE_INTERNAL_API_URL`, `LOUNGE_INTERNAL_API_SECRET`. 라운지에는 같은 환경의 `EDITOR_INTERNAL_API_SECRET`. 운영 URL은 HTTPS, ZIP 업로드는 같은 Supabase 호스트만 허용한다.
- 관측: `NEXT_PUBLIC_SENTRY_DSN`, `SENTRY_DSN`. 소스맵 업로드는 아직 설정하지 않았으며 `SENTRY_AUTH_TOKEN`은 설정 전용이다. 사용자 ID 외 이메일·코드·프롬프트·첨부·request payload·breadcrumb를 전송하지 않도록 코드에서 제거한다.
- 정리: `/api/maintenance`에 `Authorization: Bearer <CRON_SECRET>`. 코드 기본값은 삭제 프로젝트·이전 파일 버전·첨부 30일, 참조가 사라진 파일은 30일 이후 삭제 후보가 된다. **보존 기간은 운영 정책으로 승인되지 않았으며 staging에서 먼저 검증해야 한다.** 정리는 배치 제한으로 여러 번 실행해야 할 수 있다.

## 검토할 구현 선택

- 채팅은 승인·예약·프로젝트 CAS를 직접 제어하는 React UI와 NDJSON 전송을 쓴다. 계획의 assistant-ui 대신 이 구현을 채택할지 검토한다.
- 한 AI 턴에는 한 파일 변경안을 만든다. 파일별 승인과 오래된 제안 거절을 명확하게 유지한다. 여러 파일 작업은 다음 턴으로 이어간다.
- 미리보기는 opaque-origin sandbox와 CSP, 텍스트 자산 data URL을 사용한다. 현재 Chromium에서 부모 origin의 Blob 자산 로드가 차단되어 대체했다. 상대 CSS/JS/이미지와 local fetch를 해석하며 외부 fetch/리소스 로드는 차단한다. 순환 모듈, srcset, 임의 런타임 경로 계산, 외부 CDN은 지원 범위에서 제외했다. iframe 자신의 페이지 이동까지 모든 네트워크 사용을 차단하는 별도 실행 서버는 포함하지 않는다.
- 파일 생성/이름 변경은 native dialog 입력으로 구현했다. 파일 트리는 500개 상한과 CSS content-visibility를 사용하며 실제 학원 PC 300파일 성능을 확인한다. 키보드 F2/Delete, 빠른 열기, 명령 팔레트를 제공한다.
- 텍스트 256KB 초과는 읽기 전용이며 최대 5MB까지 비공개 Storage로 저장한다. 프로젝트 전체 30MB/500파일, 계정 합계 100MB, ZIP 30MB. binary size와 ZIP 디렉터리/실제 스트림 크기를 모두 검증한다.
- 파일 수정 전 원본은 `editor_file_versions`에 보관한다. 사용자용 버전 탐색 화면은 원문에서 2차 후보여서 구현하지 않았다. 복구는 관리자 검토 후 DB 버전으로 수행한다.
- 교사도 자기 프로젝트만 접근한다. 다른 학생 프로젝트 열람/관리 범위는 원문대로 2차다.

## 이메일·비밀번호 로그인 추가

로그인 화면의 기본 방식은 라운지 계정 이메일·비밀번호다. 브라우저 Supabase SDK의 `signInWithPassword`로 인증한 뒤 기존 서버 계정/활동 역할 검사와 프로젝트 소유권 검사를 거친다. 비밀번호는 에디터 API나 로그에 보내지 않으며, 로그인 시도가 끝나면 입력 상태를 비운다. 비밀번호가 없는 계정은 기존 이메일 로그인 링크 또는 카카오 로그인을 사용할 수 있다. 새 계정 생성이나 비밀번호 변경은 이 변경에 포함하지 않는다.

실제 테스트 계정의 비밀번호 로그인·로그아웃·두 계정 격리 인수는 계속 #19에서 추적한다. 자동 브라우저 검사는 가짜 Supabase Auth 응답으로 성공/새로고침 세션 유지, 잘못된 자격 증명·중복 제출 방지, 서버 계정 차단, 이메일 링크 대안을 검증한다.

GitHub App 소유자는 `quirinal36`으로 결정했다. 각 학생의 라운지 로그인과 GitHub 승인을 분리하며, 개인 저장소 가져오기·연결·변경 커밋·최신 가져오기 및 충돌 차단을 추가했다. App 등록의 GitHub 보안 재인증과 학생 본인 OAuth 승인, 시험 저장소 실제 왕복 인수는 사람이 필요한 단계다. 설정·제한·검증 기록은 [GitHub 연동 문서](./08-github-integration.md)를 참조한다.
