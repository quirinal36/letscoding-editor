### 2. 라운지 DB 변경 검토·staging 적용

원본은 **라운지 저장소**다. 에디터의 `integration/ai-learning-requests.sql`은 동일 내용의 미적용 검토본이며 별도 원장이 아니다.

1. 백업과 staging 프로젝트 ref를 확인하고 라운지의 `docs/02-database-migrations.md` 절차로 원장을 대조한다. 로컬 기본 연결이 운영일 수 있으므로 확인 없이 `db push`하지 않는다.
2. 다음 **두 migration**을 순서대로 검토·적용한다. 다른 미적용 migration도 무조건 함께 밀지 않는다.
   - `supabase/migrations/20261011152448_editor_ai_learning_requests.sql`
   - `supabase/migrations/20261011153840_refresh_qa_checklist.sql`
3. `editor.editor_ai_requests`, `editor_begin_ai_request`, `editor_ai_request_management`, `editor_cleanup_ai_requests` 및 service_role 전용 권한을 확인한다. anon/authenticated 직접 접근은 거부되어야 한다. `editor` 스키마는 기존 에디터와 같이 REST에 노출한다.
4. 라운지 조회 코드 → 에디터 선택/기록 코드 순으로 staging에 배포한다. 공유 DB 적용 완료 전에는 기록을 활성화하지 않는다.

### 3. 승인한 환경변수 설정

에디터 서버 전용 설정이다. 키 값을 문서·이슈에 붙이지 않는다.

| 설정 | 값/역할 |
| --- | --- |
| `OPENROUTER_MODELS` | 승인된 후보 ID를 쉼표로 나열, 최대 12개. 첫 항목이 신규 사용자의 기본값. 미지정 시 기존 CODE/AUX/VISION 설정 유지 |
| `EDITOR_AI_ENABLED` | 기존 AI 활성화 게이트. 키·허용 모델·양수 예산이 함께 필요 |
| `EDITOR_AI_DAILY_LIMIT_USD`, `EDITOR_AI_MONTHLY_LIMIT_USD`, `EDITOR_AI_MAX_TURN_USD` | 승인된 실제 한도 |
| `EDITOR_AI_LOGGING_ENABLED` | 정책·migration·고지 확인 후 `true` |
| `EDITOR_AI_LOG_RETENTION_DAYS` | 승인한 보존 일수. 빈 값이나 0은 승인으로 취급하지 않음 |
| `EDITOR_AI_LOG_POLICY_VERSION` | 승인 문서 버전/날짜 등. 예: 승인 후 지정한 버전 문자열 |
| `EDITOR_AI_LOG_CLEANUP_ENABLED` | 보존 정리와 중단 요청 복구를 별도로 승인해 `true` |
| `CRON_SECRET` | 기존 또는 전용 서버 비밀. 정리 엔드포인트 인증 |

`EDITOR_AI_LOGGING_ENABLED=true`인데 정책 설정이 빠지면 전송을 차단한다. 플래그가 꺼져 있으면 기존 AI 동작을 유지하며 새 학습 기록을 수집하지 않는다. 모든 설정 후 재배포하고 `/api/config`의 공개 상태와 전송 화면 안내를 확인한다.

### 4. 시험 계정으로 격리·상태 인수

시험 기관 A/B, 학생 A1/A2, 담당/비담당 교사, 기관 관리자, 플랫폼 관리자를 준비한다. 합성 프롬프트만 쓰고 운영 학생 데이터는 증거에 첨부하지 않는다.

- [ ] 학생이 모델을 선택해 전송하고 라운지 `/admin/ai-learning`에서 시간·학생·작품·선택/실제 모델·가려진 프롬프트·상태가 한 건으로 연결되는지 확인한다.
- [ ] 같은 요청 ID 재전송은 유료 호출하지 않는지, 다른 내용으로 같은 ID를 보내면 거부하는지 확인한다. 의도적 새 요청은 새 ID이며 실패 후 재전송에는 `retry_of`가 연결된다. 최초 기록 자체가 없으면 그 재시도 링크는 생략한다.
- [ ] 교사는 현재 담당 학생·현재 활성 소속·전송 당시 같은 기관인 기록만 조회한다. 목록뿐 아니라 타 학생의 상세 ID 직접 호출도 차단되어야 한다. 기관 관리자는 자기 기관, 플랫폼 관리자는 전체다.
- [ ] 담당 반 변경·교사 membership 종료·학생 기관 이동 후 이전 URL을 새로 조회한다. 새 기관이 이전 기관 기록을 볼 수 없어야 한다. 기관을 바꾸면 기존 목록·상세가 남지 않는지 확인한다.
- [ ] 정책 거절, 예산 거절, 공급자 오류, 중단, 네트워크 단절, 결과 저장 실패, 정산 실패를 시험한다. 기록 저장 장애 동안 유료 호출은 없어야 한다.
- [ ] 일반 채팅, 이미지 직접 생성(별도 기존 이미지 게이트 필요), 무료 ZIP/정책 작업을 각각 확인한다. 채팅의 이미지 도구 호출은 해당 채팅 요청 한 건에 포함한다.
- [ ] 대화·작품을 삭제해도 학습 기록이 보존되는지 확인한다. 개인 삭제 요청은 신원·권한 확인 후 담당 관리자가 처리한다. 계정의 실제 DB 삭제는 해당 기록을 cascade 삭제하지만 기존 계정 탈퇴 흐름은 별도 인수가 필요하다.
- [ ] 학생에게 보존 일수와 조회 대상이 전송 전에 보이고, 삭제 안내가 실제 보존과 맞는지 확인한다. 마스킹용 시험 토큰만 사용한다.

### 6. 정리·복구·운영 전환

- 승인 후 5–10분마다 인증된 `GET /api/maintenance/ai-learning`을 호출하는 스케줄러를 연결한다. 응답 `stale`, `purged`와 실패율을 관측한다. 한 번에 각각 최대 500건이므로 밀리면 반복 실행한다. 이 경로는 기존 프로젝트/Storage 정리와 분리되어 있다.
- 10분 이상 `received`/`running`인 요청은 `unknown`으로 전환한다. **자동 재호출·0원 정산은 하지 않는다.** 요청 ID·예약 ID·시간·모델로 공급자 사용 내역과 대사하고 필요한 경우 기존 정산 절차로 처리한다. 새 클라이언트의 유료 요청 ID와 예산 예약 ID는 동일하므로 중간 장애에도 추적할 수 있다.
- `save_failed`는 결과를 저장하지 못한 상태, `settlement_failed`는 정산 확인이 필요한 상태다. 둘 다 완료로 표시하지 않는다. `cost_kind=reserved`는 추정 예약액으로 실제 청구 확인이 필요하다.
- 만료 기록은 조회 API에서 즉시 제외되고 정리 작업에서 물리 삭제한다. 채팅/작품 FK cascade로 삭제하지 않는다. 계정 실제 삭제는 별도 cascade다. DB 백업 보존은 애플리케이션 삭제와 별도 운영 정책이다.
- 오류 시 새 수집은 `EDITOR_AI_LOGGING_ENABLED=false`, AI 사용은 필요하면 `EDITOR_AI_ENABLED=false`로 중지한다. **이미 승인된 정리 정책과 `EDITOR_AI_LOG_CLEANUP_ENABLED`는 유지할 수 있다.** 테이블을 DROP하거나 기존 기록을 비우는 롤백은 하지 않는다. 보존 일수 변경은 새 기록부터 적용하며 과거 기록의 `expires_at`은 별도 승인 없이 덮어쓰지 않는다.
- staging 인수와 위 정책 확인 후 운영 DB → 라운지/에디터 배포 → 기능 활성화 → 합성 요청 스모크 검사 순으로 전환한다. 확인 결과만 이슈에 남기고 프롬프트 원문·토큰·비밀키는 첨부하지 않는다.

## 사람이 확인해야 하는 남은 위험

실계정·실DB·공급자별 유료 도구/이미지 호환성·최종 청구·실제 기관 권한 변경·개인정보 고지·운영 백업/보존·성능은 자동 모의 검사로 확정하지 않았다. 라운지 전체 검사에 남아 있는 기존 실패 16개는 이번 에픽 밖의 별도 회귀 정리가 필요하다.
